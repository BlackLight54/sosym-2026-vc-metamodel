\section{Background}\label{sec:background}

\subsection{W3C Verifiable Credentials Data Model 2.0}\label{sec:vcdm}

The W3C \acf{VCDM} 2.0 \citep{sporny_verifiable_2025} defines a verifiable credential as a tamper-evident set of claims made by an issuer about one or more credential subjects. A \emph{claim} is a subject--property--value triple; the \emph{issuer} asserts the claims, the \emph{holder} possesses the credential and presents it to a \emph{verifier}. VCDM 2.0 standardizes this structural vocabulary but does not prescribe the domain-level semantics of claim values, the encoding format, or the privacy capabilities available during presentation. This gap between structural vocabulary and the format-specific concerns that govern real deployments motivates the multi-layer separation developed in \autoref{sec:approach}.

VCDM credentials can be serialized in multiple formats with distinct privacy capabilities. SD-JWT-VC \citep{terbu_sd-jwt-based_2026} provides hash-based \emph{selective disclosure}, allowing a holder to reveal a chosen subset of claims while withholding others. AnonCreds \citep{curran2022anoncreds} supports both selective disclosure and \emph{predicate proofs}, \acp{ZKP} that a claim value satisfies a predicate (e.g., \refi{monthly_income} \(\geq\) \refi{threshold}) without disclosing the value itself.\footnote{JSON-LD with BBS \citep{noauthor_verifiable_2024, _bbs_2024} and ISO mdoc \citep{_mobile_2021} also support selective disclosure but not predicate proofs.} The eIDAS 2.0 \ac{ARF} mandates SD-JWT-VC for EU wallet attestations \citep{noauthor_eu-digital-identity-walleteudi-doc-architecture-and-reference-framework_2026}; subsequent sections use it as the representative format.

The asymmetry between these format families is the central design axis for the analysis that follows. Selective disclosure is available across all four formats; predicate proofs are restricted to AnonCreds. When privacy regulation requires predicate proofs that the mandated format cannot provide, a cross-layer conflict emerges (\autoref{sec:headlines}).

\subsection{Multi-Layer Modeling}\label{sec:multi-layer}

Multi-layer modeling organizes a design problem into abstraction layers, each defining its own types, instances, and well-formedness rules. The three layers in \autoref{sec:approach} (domain concepts, credential schemas, and format-specific representations) are abstraction layers in this sense, but they are not related by instantiation.\footnote{Usually, in multi-level metamodeling \citep{goos_essence_2001}, each layer instantiates the one above it. Our layers do not: a credential schema is not an instance of a domain concept, but a separate representation governed by a different authority.} Each is an independently governed concern space; we formalize cross-layer relationships as graph predicates.

Each layer's constraints originate from different governance sources: sector regulation and business rules at the domain level, the W3C data model at the credential-schema level, and EU implementing acts and community specifications such as AnonCreds \citep{curran2022anoncreds} at the format level. The governance of these sources is semi-independent; for the EU Digital Identity Wallet specifically, harmonization from eIDAS through implementation directives to ETSI standards is and ongoing effort. A single-layer model that simply merges them would not be able to properly attribute a constraint to its source, so conflicts between governance sources could become undetectable.

These three foundations, the W3C credential data model and its format-specific privacy asymmetries (\autoref{sec:vcdm}), multi-layer modeling with independently governed concern spaces (\autoref{sec:multi-layer}), and partial graph modeling in Refinery (\autoref{sec:refinery}), together enable the cross-layer analysis. \autoref{sec:overview} develops the running example where they interact and defines the framework's usage modes.

\subsection{Partial Graph Modeling with Refinery}\label{sec:refinery}

During the early phase of development, our knowledge about models is often incomplete. In partial modeling \citep{famelisPartialModelsModeling2012} uncertainty can be denoted explicitly, thus a range of design alternatives can be developed together.
Refinery \citep{marussy_refinery_2024} uses a modeling methodology in which design specifications are expressed as partial models and graph predicates serve as a first-class constraint language. Refinery is based on a four-valued logic interpretation \citep{Belnap77useful} that assigns one of four truth values to every node, edge, and attribute value, enabling reasoning over incomplete (or inconsistent) specifications where both structural and data-level decisions remain open. In Refinery, nodes correspond to objects (instances of classes defined in a metamodel), and edges correspond to typed references between objects; class membership is an additional unary relation over nodes.

\textbf{Signature} \citep{marussy_refinery_2024}. A \emph{signature} defines the vocabulary of a domain model: a finite set of \emph{symbols} representing class names and reference names. Each symbol has an \emph{arity}: class names are unary (they classify individual objects), and reference names are binary (they relate pairs of objects).

\textbf{Partial model} \citep{marussy_refinery_2024}. A \emph{partial model} over a signature consists of a finite set of objects and an interpretation that assigns each class membership and each reference between objects one of four truth values: \refi{true}, \refi{false}, \refi{unknown}, or \refi{error}.

By convention, diagrams render \refi{true} values as solid lines, \refi{unknown} as dashed lines, and \refi{false} as absence. During refinement, \refi{unknown} values are committed to \refi{true} or \refi{false}; a model with no remaining \refi{unknown} values is \emph{concrete}. An \refi{error} value arises when a design decision contradicts a constraint.

\todo[inline,color=green!20]{formal: A partial model A refines B if every true or false assignment in B is preserved in A; unknown values in B may be committed to either true or false in A. Refinement is a partial order over interpretations that formalizes the monotonic narrowing of design alternatives [@semerath\_graph\_2018].}

\autoref{lst:refinery-metamodel} illustrates a fragment of the domain concept layer from \autoref{sec:approach}, simplified for exposition.\footnote{The full metamodel in \autoref{sec:approach} uses a symmetric \refi{neighbours} relation and the error predicate \refi{non_connected}; the simplified names here prioritize readability.} Classes define node types with typed references; the \refi{contains} keyword denotes ownership (composition). The derived predicate \refi{reachable} pattern-matches over the \refi{property} and \refi{value} references: it holds when entity \(a\) owns a property whose value is entity \(b\). The \emph{error predicate} \refi{disconnected} uses transitive closure (\refi{+}) to flag any pair of entities not connected by a chain of reachable steps; when it evaluates to \refi{must}, the partial model contains a structural flaw that no refinement can repair.

Graph predicates define structural constraints and derived properties over partial models. A predicate body specifies a graph pattern; the framework evaluates it over the partial interpretation under the four-valued semantics introduced above. Negation and transitive closure extend this evaluation to richer structural queries.

\textbf{Predicate satisfaction} \citep{marussy_refinery_2024}. A model \emph{satisfies} a predicate when the predicate evaluates to \refi{true} for all variable bindings. Under four-valued semantics, a conjunction of conditions evaluates to the least committed value among its operands: if any condition is \refi{unknown}, the conjunction is \refi{unknown}; if any condition is \refi{false}, the conjunction is \refi{false}; \refi{error} arises when an element is simultaneously required and forbidden. Negation and transitive closure extend analogously over the four values.

\begin{lstlisting}[style=refinery, caption={Metamodel fragment with error predicate}, label=lst:refinery-metamodel]
abstract class Entity {
    contains Prop[] property
}
class Subject extends Entity.
class Value extends Entity.

class Prop {
    contains Value[1] value
}

pred reachable(Entity a, Entity b) <->
    property(a, p), value(p, b).

error disconnected(Entity a, Entity b) <->
    a != b, !reachable+(a, b).
\end{lstlisting}

\emph{Propagation rules} derive new facts during refinement: when their precondition pattern matches with all elements committed (\refi{must}), the consequent is applied. A propagation rule with a positive consequent (e.g., \refi{Subject(e)}) infers new class memberships or edges. \emph{Negative elimination} is the dual: a propagation rule with a negated consequent (e.g., \refi{!value(p, e)}) removes design choices that would necessarily violate a constraint, setting them to \refi{must not}. Both operate incrementally during model refinement, narrowing the space of possible completions before generation explores them.

\todo[inline,color=green!20]{formal: Formally, a propagation rule fires when its precondition pattern matches with all bindings committed to true; the consequent then forces the target element to true (positive inference) or false (negative elimination). Rules are applied to a fixpoint: the engine iterates until no rule produces a new assignment, yielding a refined partial model that preserves all prior commitments [@semerath\_graph\_2018; @marussy\_refinery\_2024].}

\autoref{lst:refinery-mechanisms} demonstrates the remaining mechanisms. The propagation rule \refi{classify_root} performs positive inference: when an entity has no incoming \refi{value} reference, it is classified as a \refi{Subject}. The rule \refi{no_self_loop} performs negative elimination: when an entity owns a property, that property cannot point back to the same entity as its value. The \emph{shadow predicate} \refi{DCL} marks all entities and properties as belonging to the domain concept layer; it records derived information for inspection without constraining generation. Finally, the \emph{scope constraint} bounds the number of instances of each type, controlling the size and shape of generated models.

\begin{lstlisting}[style=refinery, caption={Propagation rules, shadow predicate, and scope constraint}, label=lst:refinery-mechanisms]
propagation rule classify_root(Entity e) <->
    must !value(_, e)
==>
    Subject(e).

propagation rule no_self_loop(Prop p, Entity e) <->
    must property(e, p)
==>
    !value(p, e).

shadow pred DCL(e) <-> Entity(e); Prop(e).

scope Entity = 3..5, Prop = 2..4.
\end{lstlisting}

Given a partial specification combining a metamodel, predicates, and instance-level assertions, Refinery applies propagation rules to derive new facts, checks error predicates, and generates concrete models that satisfy all constraints, or determines that no consistent completion exists \citep{semerath_graph_2018}. Generation is refinement-based: every generated model is guaranteed to satisfy all specified constraints (soundness), and if a constraint is violated in every possible completion, the tool detects the violation (completeness).

The multi-layer metamodel and cross-layer predicates defined in  are expressed as standard Refinery specifications, so generated credential ecosystem models inherit both guarantees.}
